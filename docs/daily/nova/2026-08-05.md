## 2. Dependências e segurança

Rodado `npm install` + `npm audit` no monorepo. `npm audit fix` resolveu a
maioria (babel, vite, postcss, body-parser, brace-expansion, ip-address).
Sobrou uma vulnerabilidade moderada do `react-router` (6.x inteira vulnerável
a open-redirect + SSR hydration issue) que só tem correção na v7.

Decisão: migrar `react-router-dom` de `^6.26.1` pra `^7.9.6` (hoje resolve pra
`7.18.2`). App usa só API declarativa clássica (`BrowserRouter`, `Routes`,
`Route`, `Link`, `useNavigate`, `useSearchParams`, `Navigate`) — sem mudança
de comportamento. Typecheck e build de produção confirmados limpos.

Restou uma última vulnerabilidade "high" (RSC Mode CSRF Bypass,
`GHSA-qwww-vcr4-c8h2`) que afeta a faixa `7.12.0-8.2.0` inteira — não existe
hoje nenhuma versão publicada que escape dela (nem existe uma 8.x ainda). Não
é explorável aqui: o app é SPA client-side puro, sem React Server Components
nem server actions. Aceito como falso-positivo documentado.

Commit `4fa3a3c`, pushado.

### 3.5 O gap de migrations do Prisma (achado importante)

Ao rodar `prisma migrate deploy` pela primeira vez, `0001_baseline` "passou"
mas `0002_tenant_status_convite` falhou com `relation "Tenant" does not
exist`. Investigando, `0001_baseline/migration.sql` está **vazio de
propósito** — o processo real desse projeto, documentado em
`config/semana-01.md`/`semana-02.md`, sempre foi criar as tabelas manualmente
via SQL Editor do Supabase (como `postgres`, dono das tabelas, pra poder
habilitar RLS) e só sincronizar o Prisma depois via `db pull`. Prisma nunca
rodou DDL de fato nesse projeto até então.

Pior: a coluna `slug` da tabela `Tenant` (adicionada na semana 4,
`config/semana-04.md`, junto com a policy de SELECT público por slug) também
**nunca virou migration rastreada** — só existe como instrução manual num doc.
Ou seja, `0001_baseline` + `0002_tenant_status_convite` sozinhos não
reconstroem o schema documentado em `docs/cerebro-do-projeto.md` (seção
"Modelo de Dados").

Solução aplicada: montei o schema final completo (Tenant com `slug`/
`status`/campos do Stripe, User, Convite, todos os enums, RLS habilitado +
todas as policies canônicas, grants pro `app_user`) manualmente como
`postgres`, direto a partir do que já estava documentado no cérebro do
projeto. Depois, `npx prisma migrate resolve --applied` nas duas migrations
(sem executá-las de verdade — só marca como aplicadas no
`_prisma_migrations`).

**Pendência criada:** falta uma migration real (`0003`, algo tipo
`tenant_slug`) que feche esse gap no histórico do repo — hoje só funciona
porque alguém (eu, hoje) sabe montar o schema na mão a partir da documentação.
